# Armory Intendant: правила разработки

Этот файл — источник правил для людей и coding-агентов, которые добавляют или меняют код проекта. Он описывает целевую архитектуру. Старые закомментированные реализации, файлы `*Old*`, `trash` и отдельные текущие классы с несколькими ответственностями не являются образцами для нового кода.

## Контекст проекта

- Стек: Phaser 3.90, TypeScript в `strict`-режиме, Vite.
- Исходники находятся в `src`; Vite использует `src` как root и собирает приложение в `dist`.
- Основная проверка проекта: `npm run build` (`tsc` и затем production build Vite).
- Автоматических тестов и линтера пока нет. Для рискованных изменений обязательна ручная проверка затронутого игрового сценария.
- Используй alias `@/` для импортов из `src`, `@assets/` для ресурсов и `@fonts/` для шрифтов.

## Архитектура и направление зависимостей

Придерживайся следующего разделения:

```text
Scene → Renderer/coordinator → View/Partial/Behavior
  │             │                    │
  └────────→ Service/System ←────────┘
                │
          Store + Data + Types
```

- `src/scenes/*Scene` управляет Phaser lifecycle, переходами между сценами и связывает крупные подсистемы. Сцена не должна содержать подробную отрисовку или боевые формулы.
- `*Renderer` координирует экран: читает состояние, создаёт partial/view, синхронизирует коллекции и управляет их lifecycle. Renderer не должен вручную рисовать сложную сущность, если её можно выразить отдельным view.
- `src/partials` содержит визуальные сущности и переиспользуемые UI-компоненты. View отвечает за своё дерево Phaser Game Objects и локальные анимации, но не принимает игровые решения.
- `*Behavior` инкапсулирует переиспользуемое интерактивное поведение: drag, hover, selection и похожие механики. Поведение общается с владельцем через typed config и callbacks.
- `src/services` содержит игровую и инфраструктурную логику: бой, статусы, способности, аудио, сохранения, навигацию. Не импортируй сюда сцены, renderers или UI partials.
- `src/store` — долгоживущее состояние забега. Изменения состояния должны проходить через понятные методы store/system, а не быть побочным эффектом рендера.
- `src/data` — декларативный игровой контент и таблицы конфигурации. Здесь не должно быть lifecycle-кода и мутаций UI.
- `src/styles` — единый источник цветов, типографики, шрифтов и метрик.
- `src/utils` — небольшие чистые или инфраструктурные функции без скрытого состояния конкретной сцены.

Если класс одновременно хранит доменное состояние, рисует UI, подписывается на input и реализует игровое правило, раздели его на coordinator, view и behavior/system.

## Куда помещать новый код

- Новая сцена: `src/scenes/<Name>Scene/`, отдельно `NameScene.ts`, `NameRenderer.ts` и при необходимости `NameConfig.ts`/`NameLayout.ts`.
- Визуальная сущность боя: `src/partials/battle`.
- Универсальный UI-компонент: `src/partials/ui/components`.
- Композиция нескольких UI-панелей: `src/partials/ui`.
- Игровое правило или расчёт: соответствующий system/service, а не renderer.
- Статический контент: `src/data`; его контракт — в явном TypeScript-типе.
- Локальный тип компонента держи рядом с компонентом. Общий доменный тип выноси в отдельный импортируемый `.ts`-модуль; не расширяй `declare global` без необходимости. Module augmentation допустим только для реального расширения Phaser API.

## Именование

- Классы, типы и интерфейсы: `PascalCase`; методы и переменные: `camelCase`; константы уровня модуля: `UPPER_SNAKE_CASE`.
- Имя должно описывать роль: `BattleRenderer`, `LootView`, `DraggableItemBehavior`, `CombatSystem`.
- Методы, которые добавляют или перестраивают визуальные объекты, называй `render...`: `renderBackground`, `renderItemIcon`, `renderStatusBar`.
- Не добавляй пользовательские методы с префиксами `create...` и `draw...`. Исключение — обязательный lifecycle-метод Phaser `Scene.create()` и вызовы Phaser API вроде `graphics.draw...`, если у API нет другого имени.
- Для невизуальных действий используй точный глагол: `generate...`, `build...`, `resolve...`, `calculate...`, `bind...`, `setup...`, `sync...`, `remove...`, `destroy...`.
- `render()` должен быть понятной точкой входа визуальной сущности. По возможности делай повторный вызов безопасным и не создающим дубликаты.
- Не используй неопределённые сокращения и названия вроде `GO`, `data2`, `managerStuff`, `tmp` в постоянном коде.

## TypeScript

- Сохраняй совместимость с `strict: true`; новая функциональность не должна опираться на `any`, `as any` или необоснованный non-null assertion.
- Для публичных методов указывай возвращаемый тип. Зависимости и неизменяемые поля отмечай `readonly`.
- Используй конкретные Phaser-типы и typed config/callback interfaces вместо неструктурированных объектов и строковых data bags.
- Проверяй lookup по ID до использования: неизвестный `itemId`, texture key или definition должен иметь явный fallback либо понятную ошибку.
- Не дублируй один доменный интерфейс в store, `.d.ts` и компоненте. Перед добавлением типа проверь `src/types`, `src/store` и соответствующий `src/data`.
- Для конечного набора состояний предпочитай union или enum произвольной строке.
- Не скрывай ошибку пустым `catch`. Либо обработай её, либо добавь контекст и пробрось дальше.

## Phaser lifecycle и владение ресурсами

- У каждого view должен быть очевидный владелец. Если класс наследует `Phaser.GameObjects.Container`, добавь его в сцену через `scene.add.existing(this)` и держи дочерние объекты внутри root-контейнера.
- Любая подписка через `.on(...)` требует симметричной `.off(...)`. Используй именованные handlers или сохраняй disposer; не создавай неотписываемые анонимные обработчики для долгоживущих объектов.
- Подписки на `UPDATE`, `PRE_RENDER`, input, timers и scene events обязательно очищай в `destroy()` или на `Phaser.Scenes.Events.SHUTDOWN`.
- В `destroy()` останавливай принадлежащие объекту tweens, удаляй masks, tooltip bindings, timers, sounds и behaviors. Метод должен безопасно переносить повторный вызов.
- Перед полной перерисовкой сначала вызывай cleanup владельцев, затем удаляй scene children. Не оставляй ссылки на уже уничтоженные Game Objects.
- Не запускай два tween, одновременно управляющих одним свойством одного target. Используй вложенные контейнеры или последовательность tween.
- Tooltip обычно один на renderer/coordinator и обслуживает несколько targets. Не создавай отдельный `Tooltip` внутри цикла, если визуально одновременно нужен только один.
- Behavior не должен владеть доменной моделью. Он меняет Phaser target и сообщает о событиях владельцу через callbacks.

## Рендеринг и состояние

- Renderer — координатор, а не «мешок методов». Он хранит map/view registry, делегирует визуал partial-классам и вызывает systems для игровых действий.
- View получает готовые данные или readonly domain object и не изменяет `GameState`, rewards или combat rules.
- `render...` не должен неожиданно изменять игровую модель. Отделяй команды (`spawnLoot`, `applyDamage`, `completeNode`) от визуализации (`renderLootView`, `renderDamageEffect`).
- Для динамических коллекций используй `Map<id, View>` и синхронизацию по стабильному ID вместо поиска по Phaser metadata.
- Отделяй очистку представления от сброса модели: `clear()` может демонтировать view, а `destroy()` — окончательно освободить владельца. Семантика должна быть явно задокументирована кодом.
- Координаты, размеры, durations и depth, повторяющиеся более одного раза или имеющие смысл для дизайна, выноси в config/layout или именованные константы.

## UI, layout и assets

- Используй `COLORTOKEN`, `TYPETOKEN`, `FONTTOKEN` и `METRICTOKEN`. Не добавляй произвольный цвет, шрифт или размер, если значение является частью дизайн-системы.
- Локальные служебные цвета допустимы для debug/fallback, но должны быть именованными и не подменять UI-токены.
- Для границ экрана используй `viewBounds`/`screenBounds`; layout конкретной сцены держи в её `*Config.ts` или `*Layout.ts`.
- Не размазывай по компоненту magic numbers. Группируй размеры, gaps, offsets, durations и depths в typed scheme или константы.
- Изображения и аудио загружаются автоматически через `ImageAssets`/`AudioAssets`, а ключ равен имени файла без расширения. Имена файлов должны быть уникальны внутри всех glob-папок соответствующего типа.
- При необязательной текстуре предусматривай контролируемый fallback. Не передавай пустой texture key в отображаемый объект без проверки.
- Текст интерфейса и игровой контент сейчас русскоязычные; сохраняй стиль существующего текста и не смешивай языки внутри одной пользовательской строки.

## Данные, store и системы

- Записи в `Heroes`, `Squires`, `Enemies`, `Items`, `Abilities` и `Statuses` должны соответствовать типизированному контракту. Ключ таблицы и поле `id` должны иметь предсказуемую связь.
- Не импортируй UI-токены в игровые системы. Допустим обратный путь: view может читать data и tokens.
- Случайность держи возле системы, которая принимает решение, и предпочитай `Phaser.Math` в игровом runtime. Не разбрасывай случайные формулы по renderer/view.
- Сериализуемое состояние не должно содержать Phaser Game Objects, scene references, tweens или callbacks.
- При изменении формата сохранения продумай нормализацию старых данных и безопасный fallback до включения записи в `localStorage`.

## Чистота кода

- Не оставляй большие закомментированные реализации, временные альтернативы, `*Old*`, `trash` и мёртвые импорты. История хранится в Git.
- Не оставляй `console.log` в завершённой функциональности. `console.warn/error` допустимы для действительно диагностируемой проблемы и должны содержать контекст.
- Не смешивай функциональный рефакторинг с массовым форматированием несвязанных файлов.
- Сохраняй существующие изменения пользователя и проверяй `git status` перед работой.
- Предпочтительный стиль нового кода: четыре пробела, одинарные кавычки, trailing commas в многострочных структурах, точки с запятой, imports через alias.
- Один файл — одна основная публичная сущность. Если класс становится трудно просмотреть целиком или у него больше одной причины для изменения, выдели view, behavior, layout/config или system.
- Комментарий должен объяснять причину или ограничение, а не пересказывать строку кода. Для будущей работы используй короткий `TODO` с конкретным условием завершения, а не закомментированный код.

## Рабочий процесс для новой задачи

1. Прочитай этот файл и ближайшие к задаче scene/renderer/partial/system.
2. Проверь `git status` и не перезаписывай чужие незавершённые изменения.
3. Сформулируй, где живёт состояние, кто координирует, кто отображает и кто владеет cleanup.
4. Делай минимальный связный diff; не исправляй весь проект попутно.
5. После изменения запусти `npm run build` и `git diff --check`.
6. Вручную проверь затронутый путь: первый render, повторный render, interaction, edge/fallback и shutdown сцены.
7. В итоговом сообщении перечисли изменённое поведение, файлы и выполненные проверки.

## Definition of Done

Изменение считается завершённым, когда:

- ответственность кода соответствует слоям выше;
- нет новых `any`, утечек listeners/tweens и дублирующихся визуальных экземпляров;
- UI использует токены и scene layout;
- отсутствует закомментированный старый код и временный debug output;
- `npm run build` и `git diff --check` проходят;
- вручную проверены основной сценарий, повторный render и scene shutdown;
- документация обновлена, если изменился публичный контракт или структура проекта.
